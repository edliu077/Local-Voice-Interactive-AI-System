# 本地语音交互AI系统（Local Voice-Interactive AI System）— Why Windows Rebuild

本文解释已有有效Demo Stable基线后，为何选择新的数字人呈现路线和独立开发工作区。Windows Rebuild是开发阶段名，不是另一个正式项目名。本迁移分支已完成Rebuild源码静态迁入，但公开发布、完整构建和独立恢复尚未通过；没有在本副本启动七服务。

## 已有成果是起点

早期Demo Stable已串起Silero VAD、Faster-Whisper Small CPU INT8、Qwen3-1.7B CPU-only、Qwen3-TTS 0.6B Base CUDA、WebSocket、Next.js、Browser Audio和Live2D/RMS口型。目标设备的1/2/6轮人工功能回归、播放ACK、半双工和生产前端检查已有记录。

Live2D减少额外视频推理负担，为TTS保留资源，是当时有效的设计。旧版实现了核心目标，并不是因“完全不能工作”才重做。旧next dev/Turbopack OOM已通过生产构建/运行模式解决，是先前稳定化案例，**不是此次架构重构的直接原因**。

## 改变的是数字人呈现目标

后续用户明确选择参考LiveTalking路线，改用Wav2Lip音频驱动视频数字人，同时保留Windows原生、本地处理和现有语音成果。与浏览器Live2D的RMS参数驱动相比，这引入了不同的画面生产、口型推理及音视频传输职责。

现有证据支持这项明确的技术呈现选择；不补写旧版功能失败、商业需求、用户规模或未经确认的动机，也不声称新方案在所有性能和质量指标上优于旧方案。

## 为什么独立工作区，而不是在稳定目录继续叠加

新路线涉及依赖环境、GPU视频任务、外部TTS音频格式、WebRTC、进程树与缓存/输出边界。直接在旧稳定目录改造会让已验证基线与未验证新组件交错，降低回退和证据归属的清晰度。

独立Windows Rebuild目录用于分阶段施工、保护原开发/审查/Demo Stable目录、只读复用已有权重和程序，并让新增日志、缓存、PID/owner和诊断数据留在新目录。它不是从零重写所有业务，也不要求重新下载同一模型。

Git迁移采用独立审查副本并保留旧七提交，遵循同一保护思路；此处没有对保护目录进行移动、清理或覆盖。

## 被复用的模块与经验

- VAD采集、Small CPU INT8识别、llama.cpp兼容请求、1.7B与TTS模型/克隆参考的既有验证成果。
- 持久模型服务、半双工、播放后恢复Listening、WebSocket状态/字幕及原前端基础。
- 既有上下文/摘要和质量保护工作在Rebuild中沿用；不将其倒写为旧Demo Stable已验收能力。
- 已有资源测量、逐组件验证、生产前端运行、明确回退、模型/声音/素材与源码分离的工程经验。

复用不等于完全没有适配：Rebuild隔离了可写路径，更新LLM路由/归属，适配TTS与数字人音频接口及新管理器。历史CYBER_*变量、目录和内部alias等兼容标识保留，不为正式文档命名做无关代码替换。

## 新能力及其实际边界

| 新能力 | Rebuild中的作用 | 不能扩大为的结论 |
| --- | --- | --- |
| LiveTalking + Wav2Lip256 | 消费外部TTS音频，产生音频驱动的视频数字人 | 所有口型/画面质量或商业许可均已解决 |
| Avatar控制器与音频桥 | 管理本地数字人会话、音频提交与播放相关控制 | 完整公网、多用户或生产认证体系 |
| WebRTC | 向浏览器交付数字人音视频，保留WAV备用模式 | 有了连接即代表无冻结、无丢包或真实声学播放完成 |
| 七服务管理 | 顺序preflight/READY、身份检查、资源监护、自有进程安全回收 | 所有异常、所有主机及无限时长运行已通过验收 |
| 产品化流程 | 一次用户点击连接/解锁音频/开始，默认数字人音轨、明确结束 | 无需用户交互即可自动录音/发声 |
| 无限会话生命周期 | 取消正常会话六轮自动结束，有界上下文仍保留 | 无限记忆或长期对话质量保证 |

Rebuild当前服务为Next.js3000、Avatar控制器8011、TTS8765、LiveTalking8010、LLM8081、STT8766、WebSocket/VAD8767。旧Demo Stable的LLM端口8080不能混用。

## 新成本与已遇到的工程问题

新视频推理与编码/传输增加CPU/GPU工作、RAM共同驻留和音视频同步成本；不能只凭显存未满推断实时帧率足够。TTS和LiveTalking需要不同依赖环境，CUDA轮子、PyAV/aiortc、音频库及本机工具路径带来恢复成本。

进程生命周期也更复杂：Windows控制台辅助进程的受限参数变化、短生命周期探测/监控进程、创建与轮询竞态、启动调用输出句柄等待、部分启动和owner对账都曾需要定位。已有修复保留身份/资源保护，不把未知进程因退出就视作合法；部分历史PID来源仍无法证明。

TTS参考路径触发第三方FFmpeg探测，后改用支持的数组输入路径；NVML采样与创建时登记减少已证实短进程竞态。每项修复的离线检查、真实独立READY、重复启停稳定性及整机验收必须分开表述。

曾出现数字人音轨断续/画面冻结，增加有界诊断后近期短测试未明显复现，不能由此保证长期无问题。这些是路线增加的工程边界，不用于贬低旧版或掩盖当前未验收项目。

## 为什么最终仍用Qwen3-1.7B CPU-only

目标设备仍为16GB RAM和8GB VRAM，TTS与Wav2Lip共同占用GPU及系统内存。4B的独立可运行不等于七服务共同驻留具有安全余量；有限的CPU、Hybrid和分时评估未形成值得作为正式连续语音路线推进的依据。

用户最终明确停止4B相关路线，恢复已有验证的Qwen3-1.7B Q4_K_M CPU-only，保留4096上下文和8081接口，把优先级放在整条语音链可用。后来1.7B独立生成和整机功能有真实验证，但不代表选择1.7B便自动消除资源/识别/生成质量风险。

本文件只记录决定及已有证据，不追加模型比较、GPU层数研究、串行卸载或内存门槛调整。

## v1.0-rc1功能边界与开放问题

冻结名称为**Windows Functional Stable Candidate v1.0-rc1 — Known Quality Issues**。用户确认七服务联启、首次点击、数字人连续8轮流程、主动结束、WAV回退及安全关闭；冻结关联后台日志实际含12轮完成和下一轮主动停止，两个口径分别保留。

- **Q-001 OPEN**：已确认个别漏识别和替换，另有发音因素。三句取证完成，但没有证明VAD提前截断，早前多轮渐进恶化原因仍未知。
- **Q-002 OPEN**：历史部分回复在重试后仍重复；后来六轮完整Trace未复现明显重复且未触发重试，不能宣称重试已修好或重复永久消失。
- 长期稳定性、全部异常恢复、完整独立恢复及广泛硬件兼容没有完整验收。快照哈希校验、服务READY、功能流程与对话质量是不同证据层级。
- 当前开发副本含冻结后默认关闭的STT取证补丁，不能称其与原rc1归档字节一致；本次不更改冻结归档。
- 公共源码还需配置模板、依赖恢复配方、第三方改动、素材权利及隐私审查。外部资产缺失的源码包不应称开箱即用完整独立运行副本。
